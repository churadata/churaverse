# 開発時の watch と追加改善候補

PR #565 の watch 改善を、プラグインのエントリポイント整理が入った main
(`a9e6f927`) に移植した。main に取り込まれた変更は差分から除き、開発時の監視処理を対象にする。

## 今回の変更

- 73パッケージの `tsc --watch` を、project references を使う1つの `tsc -b --watch` にまとめる。
- 生成した tsconfig は内容が変わった場合だけ更新する。削除されたパッケージの設定とキャッシュは取り除く。
- アセット監視では、出力ディレクトリを探索前に除外し、画像・CSS・SCSS以外のファイルを監視対象から外す。
- 入れ子のプラグインのアセットも、そのパッケージ自身の `dist` にコピーする。削除も `dist` に反映する。
- ターミナルを閉じた場合も子プロセスを終了する。

型検査や source map は維持する。生成設定とビルド情報は `.dev-state/tsc` に保存する。

## 計測・確認結果

2026-10-06、macOS、Node.js 22.23.2、pnpm 10.28.1、TypeScript 5.9.3で計測。
単発の計測なので、環境やキャッシュ状態によって値は変わる。

| 対象 | 結果 |
| --- | --- |
| 73パッケージの強制フルビルド | 約7.23秒、子プロセスの最大RSS 約789 MiB、型エラーなし |
| 変更なしのビルド | 約0.58秒 |
| ビルド済みの状態から watch を起動 | 型エラーなしで待機、tsc のRSS 約142 MiB |
| アセット監視のエントリ数 | main の1,878から582へ減少 |
| アセット監視開始時のRSS | main の約100 MiBから約76 MiBへ減少 |

watch 待機時の値は、変更を繰り返した後のメモリ量を表すものではない。
アセット監視のエントリ数は `chokidar.getWatched()` のファイル・ディレクトリ名の合計で、
OSが保持する監視ハンドル数とは異なる。メモリの値にはアプリやDockerを含めていない。

生成を繰り返しても74個の設定ファイルの更新日時が維持されること、不要な設定とキャッシュの削除、
入れ子のプラグインのアセット追加・変更・削除とコピー先、TypeScriptファイルの除外を確認した。
変更した3スクリプトの構文・Biomeチェックも通過。Dockerを含む `pnpm dev` 全体は未確認。

## 次に検討する改善

1. **初回ビルドの二重実行を減らす。** 現状は初回に Turbo で各パッケージをビルドし、続いて
   開発用の別設定で tsc watch を起動する。初回から開発用の `tsc -b` とアセットコピーを使えば、
   多数のコンパイラの起動と再コンパイルを減らせる可能性がある。watch の初回ビルド完了を待ってから
   アプリを起動する仕組みと、全パッケージの build スクリプトの処理を引き継ぐ必要がある。
2. **パッケージ変更による backend の再起動をまとめる。** 上流変更で複数の dist が更新されると、
   tsx watch が途中状態で何度も再起動する可能性がある。実際の再起動回数を計測し、
   ビルド完了通知か短い待機時間でまとめる方式を検討する。
3. **共有型定義の重複を調べる。** Phaserなどの異なるバージョンが依存関係に含まれるため、
   統一できれば型定義の読み込みを減らせる可能性がある。API互換性と実行時の動作確認が必要。

`assumeChangesOnlyAffectDirectDependencies` は間接依存先の型エラーを見落とす可能性があるため、
今回は採用していない。説明は [TypeScriptの公式ドキュメント](https://www.typescriptlang.org/tsconfig/assumeChangesOnlyAffectDirectDependencies.html)
を参照。
